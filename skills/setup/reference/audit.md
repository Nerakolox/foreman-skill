# 体检清单

体检只读不写，查完按文末格式出报告。每一项的结果标 ✅ 通过、⚠️ 有问题但不紧急、❌ 必须改。

开查之前先认结构（见 [architecture.md](architecture.md)「两种摆法」「其他结构怎么套」，判断顺序见 SKILL.md 第 1 步）：A、monorepo（算 A）、B、单仓、规则放在业务仓里。下面说的「总管」，A 方案就是项目根，B 方案是总管目录，单仓就是仓根。

单仓不查第 2、6、10、11、15、16 项，报告里这几项写「— 不适用」。规则放在业务仓里的，照常逐项查，第 16 项判 ❌，写明原因。

## A. 入口文件

1. **总管 CLAUDE.md**：有没有？有的话，是否具备优先级链、派发表、速查表、目录戒律这四块，缺哪块就列出来。单仓不要求派发表。
2. **包工头规则会不会泄漏**：总管 CLAUDE.md 里「不改代码」「只派活」这类话，有没有限定成「在总管目录启动时」。没限定就判 ❌，因为子仓会话也会读到它。
3. **行数**：统计每个 CLAUDE.md 和 AGENTS.md 的行数。超过 200 行判 ❌，150 到 200 行判 ⚠️。同一目录下 `.claude/rules/` 里没写 `paths:` 的文件，启动时也会整份读进来，另外列出「开局实际读入」的合计行数。
4. **`@` 引用**：在所有 CLAUDE.md 和 AGENTS.md 里找 `@路径`，反引号和代码块里的不算，AGENTS.md 里指向同目录 CLAUDE.md 的 `@CLAUDE.md` 也不算。列出被引用的文件和它们的行数，这些在启动时会整份读进来。引用 `.agents/rules` 下的细则判 ❌。
5. **AGENTS.md**：规则应该写在 CLAUDE.md，AGENTS.md 只给别的 AI 工具指路（见 architecture.md）。逐个目录看：
   - AGENTS.md 里有自己的规则内容，它所在目录或上层又有 CLAUDE.md：Claude Code 现在读不到它，判 ❌，写明「这份文件在 Claude Code 里不会被读取」
   - AGENTS.md 有内容、上面还没有 CLAUDE.md：改造时一加 CLAUDE.md 就会失效，判 ⚠️
   - 有 CLAUDE.md、旁边没有 AGENTS.md：判 ⚠️，写明「用 Codex、Cursor 这类工具的人读不到规则」
   - AGENTS.md 只是指向同目录的 CLAUDE.md；或者反过来，内容在 AGENTS.md、同目录 CLAUDE.md 写了 `@AGENTS.md`：✅

## B. 子仓

6. **子仓 CLAUDE.md**：每个子仓有没有。有的话，开头是否先划边界（本仓只做什么、别的仓不碰、开工先读 spec、对不上就停），有没有「spec 里没有的不许引进来」这条红线。
7. **细则怎么被指到**：列出总管和每个子仓的 `.agents/rules/`（以及 `.claude/rules/`、`.cursor/rules/`、`docs/rules/` 这类同等目录）下的文件，逐个看 CLAUDE.md 里怎么提它：
   - 写进了「主题 / 路径 / 什么时候读」的表，或者至少写了路径和读取时机：✅
   - 只甩了文件名，或者只有路径没有时机：⚠️
   - 用 `@` 引用：❌（第 4 项已记）
   - 没有任何地方提到它，成了孤儿：⚠️
   - 在 `.claude/rules/` 里、没写 `paths:` 的：不管 CLAUDE.md 怎么写，它都是一启动就读。判 ⚠️，写明「这份细则其实开局就全部加载，不是按需读取」
8. **CLAUDE.md 里的长规范**：子仓 CLAUDE.md 里有没有大段的代码风格、组件规范、提交规范原文，这些应该拆进 `.agents/rules/`。

## C. 契约

9. **单一契约源**：有没有 `spec/` 或者同等的地方（OpenAPI 文件、共享类型包、接口文档）。有好几处的，全部列出来。monorepo 里被多个端引用、或者名字像 `shared`、`types` 的包也算一处。OpenAPI 这类文件要看清是手写的还是代码生成的（`package.json` 里有 `openapi:generate` 这类脚本、文件头写着自动生成），在说明里写明。
10. **契约被复制**：同一个接口或字段的定义，是不是在多份文档里都有一份原文。
11. **跨仓对不上**：抽查几个核心实体（用户、订单这类在多个仓都出现的），比对前端的类型定义、请求代码和后端的模型、路由：
    - 字段名：`userName` 对 `username`
    - 接口路径和方法：`PATCH /api/user/profile` 对 `POST /api/users/profile`
    - 错误码、枚举值
    先看有没有统一的转换层（比如后端序列化时自动把 snake_case 转成 camelCase）。有转换层、转换后能对上的，不算冲突。每条冲突都要写清楚两边的文件位置。

## D. 目录

12. **总管目录零散文件**：列出总管目录下的顶层文件和目录，排除 CLAUDE.md、README、LICENSE、.gitignore、各种工具配置、子仓目录，以及本项目的既有类别（法律合规文本目录、品牌元信息文件这类，看总管 CLAUDE.md 里有没有登记）。剩下的 `.md`、`.txt` 笔记、草稿、排查记录，逐个判断它应该去哪（按 [architecture.md](architecture.md) 的归属表）。零散文件一个都没有时，这一项算 ✅。
13. **失效路径**：所有 CLAUDE.md、AGENTS.md、`.agents/rules/` 里提到的文件和目录路径，逐个检查是否存在。写成绝对路径的（`/Users/…`、`C:\…`），就算在本机存在也判 ❌，写明「换一台机器就失效，改成相对路径」。

## E. 施工记录

14. **任务台账**：总管有没有 `plan/tasks.md` 或者同等的全局任务表（`TODO.md`、`tasks.md`、`ROADMAP.md` 这类）。没有判 ❌。有的话，看状态是不是只用规定的几个值，有没有「做完了」但没改状态的行（任务单已归档、台账还是开发中这类）。
15. **任务单**：有没有 `joint-tasks/` 或类似的地方。有的话，看有没有状态已经是 done 但没归档的，每张任务单在台账里有没有对应的一行。

## F. 摆法和 git

16. **子仓能不能读到总管**：
    - A 方案：用 `git status`、`git ls-files -s` 看外层是不是 git 仓。外层是 git 仓、子仓也各自有 `.git` 的，外层 `.gitignore` 要逐个忽略子仓目录；没忽略判 ❌。外层已经把子仓存成 gitlink（`git ls-files -s` 里 mode 是 `160000`、又没有 `.gitmodules`）判 ❌，写明「别人克隆外层仓拿不到这个子仓」。
    - monorepo：只有一个 git 仓，不查 `.gitignore`。子仓不在第一层的（`apps/web/`），看它的 CLAUDE.md 指向总管的路径层级对不对（`../../spec/`，不是 `../spec/`），不对判 ❌。
    - B 方案：每个子仓 CLAUDE.md 有没有写启动命令，命令里是否**同时**有 `CLAUDE_CODE_ADDITIONAL_DIRECTORIES_CLAUDE_MD=1` 和 `--add-dir <到总管的路径>`。只有 `--add-dir` 的判 ❌，写明「这样启动读不到总管规则，而且不报错」。有没有「看不到总管规则就停」的自检，没有判 ⚠️。
    - 规则放在业务仓里：判 ❌，写明「这个仓的每个会话都会读到管全局的规则，包工头和干活的角色打架；其他端改契约要去改这个仓」，建议另建总管。

```markdown
子仓：`app/`（<一句话职责，从代码推断>）、`backend/`（…）…

版本管理：<每个仓是否是 git 仓、有没有未提交的改动>
共享包：<monorepo 才写：`packages/shared`（<一句话>）…；没有就删掉这一行>

| # | 检查项 | 结果 | 说明 |
| --- | --- | --- | --- |
| 1 | 总管 CLAUDE.md | ❌ | 没有这个文件 |
| … | … | … | … |

### 跨仓对不上的地方
| 实体 | 一边 | 另一边 | 位置 |
| --- | --- | --- | --- |

### 总管目录零散文件
| 文件 | 内容是什么 | 建议去哪 |
| --- | --- | --- |

<最严重的三个问题，一句话一个>
```
