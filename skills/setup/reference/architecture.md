# 架构定义

foreman 搭出来的工程都以本文件为准。生成或改造任何文件之前，先对照这里。

## 两种摆法

总管和子仓有两种摆法，都支持，**默认用 A**。判据是「子仓是不是你说了算」，不是有几个仓。

| | A 总管包住子仓（默认） | B 总管和子仓平级 |
| --- | --- | --- |
| 适合 | 自己的产品，几个端一起开发 | 子仓是上游 fork、独立发布、权限分开，不能放进总管目录 |
| 子仓会话读不读得到总管规则 | 自动读到，总管在它的上层目录 | 读不到，必须带启动参数，见下 |
| 忘了启动参数会怎样 | 没有参数可忘 | **静默失效**：不报错，AI 不知道 spec 存在，回到瞎编字段 |
| 子仓到总管的路径 | `../` | `../<总管目录>/` |

### A. 总管包住子仓

```text
<项目根>/                  总管（一个 git 仓，或者整个项目就是一个 git 仓）
├── .gitignore             子仓是独立 git 仓时，必须在这里忽略它们
├── CLAUDE.md              包工头：只派活
├── .agents/rules/         总管自己的细则：joint-tasks.md、plan.md 等
├── spec/                  契约：唯一真理源
├── plan/tasks.md          任务台账：所有任务的进度
├── joint-tasks/           正在做的跨仓任务单
├── _archive/              归档
├── <子仓 A>/              独立 git 仓，或者只是子目录
│   ├── CLAUDE.md          子仓总规：先划边界
│   └── .agents/rules/     细则，指了才读
└── <子仓 B>/ …
```

- 外层套 git、里面的子仓各自是 git 仓，完全可行。**唯一的硬规定**：外层 `.gitignore` 里逐个写上子仓目录（`app/`、`backend/`……）。不写的话，外层 `git add .` 会把子仓存成一个空指针（gitlink），别人克隆外层仓拿不到子仓内容。
- 不要用 git submodule，除非你真的需要「总管某个版本对应子仓某个版本」。submodule 会让子仓每次提交都在外层显示成改动。
- 提交要分仓做：总管的文件在外层仓提交，子仓的 CLAUDE.md 和 `.agents/rules/` 在子仓提交。

### B. 总管和子仓平级

```text
<工作区>/                  普通文件夹，不是 git 仓
├── <总管目录>/            总管 git 仓，内部结构同 A 的项目根，只是没有子仓
├── <子仓 A>/              独立 git 仓
└── <子仓 B>/ …
```

在子仓里启动的会话，默认读不到总管的 CLAUDE.md，因为平级目录不算上层。必须这样启动，**两样缺一不可**：

```bash
CLAUDE_CODE_ADDITIONAL_DIRECTORIES_CLAUDE_MD=1 claude --add-dir ../<总管目录>
```

- 只加 `--add-dir` 不够：它只给文件访问权限，总管的 CLAUDE.md 照样不加载，而且不报错。
- settings 里的 `permissions.additionalDirectories` 也不行，它同样只给文件访问权限。
- 所以 B 方案的每个子仓 CLAUDE.md 都要写明这条启动命令，并加一条自检：上下文里看不到总管规则，就停下来让用户用这条命令重启。
- 总管会话要看子仓代码时，用 `--add-dir ../<子仓>` 启动，或者会话里 `/add-dir`。
- 总管仓的 README 里维护一张版本表：总管的某个提交对应各子仓的哪个版本。

## 四层和优先级

| 层 | 文件 | 放什么 | 不放什么 |
| --- | --- | --- | --- |
| 1 契约 | `spec/` | 字段、接口、错误码、鉴权、命名、设计决策 | 实现细节、某个仓自己的约定 |
| 2 包工头 | 总管 `CLAUDE.md` | 派发表、速查表、目录戒律、优先级 | 任何一个仓的代码规范 |
| 3 子仓总规 | `<子仓>/CLAUDE.md` | 边界、红线、常用命令、细则的读取时机 | 长篇规范原文 |
| 4 细则 | `.agents/rules/*.md`（总管和各子仓都可以有） | 代码风格、组件设计、git 规范等长规则；总管的放所有仓共用的 | 契约内容 |

冲突时按这条链判：`spec/ → 总管 CLAUDE.md 和总管细则 → 子仓 CLAUDE.md → 子仓细则 → 代码`，上面的说了算。代码跟 spec 冲突，改代码，不改 spec。

Claude Code 不会自己判断谁优先，它只负责把文件读进来。所以这条链必须写进总管 CLAUDE.md 和每个子仓的 CLAUDE.md。

`plan/` 和 `joint-tasks/` 不是规则层，是施工记录：只能引用 spec 章节号，不能自己定义字段、接口、错误码。

## 三种读取时机

分层是为了配合 Claude Code 的读取时机：

| 时机 | 读什么 | 在这套结构里 |
| --- | --- | --- |
| 一启动就读 | 启动目录及所有上层目录的 `CLAUDE.md` | A 方案里包工头永远在线；B 方案要靠启动参数 |
| 碰到才读 | 子目录的 `CLAUDE.md`，Claude 读到该目录下的文件时才加载 | 活派到哪个仓，哪个仓的规矩生效 |
| 指了才读 | `.agents/` 下的文件不会自动加载，Claude 看到 CLAUDE.md 里写的路径、觉得该看，才会打开 | 细则，不占开局上下文 |

注意 `.claude/rules/` 和 `.agents/rules/` 不一样：`.claude/rules/` 里的文件，没写 `paths:` 的一启动就全部读进来，等于写在 CLAUDE.md 里；写了 `paths:` 的，碰到匹配的文件才读（已实测）。

由此得出几条硬规定：

- **每个 CLAUDE.md 不超过 200 行**。这是官方建议，超过了遵守率下降。
- **细则不许用 `@` 引用**。`@路径` 会在启动时把整个文件读进来，分层就白做了。需要提到路径时用反引号包住，比如 `` `.agents/rules/git.md` ``，反引号里的 `@` 不会触发引用。
- **指向别处的文件，一律写成表**：「主题 / 路径 / 什么时候读」三列。只甩一个文件名，Claude 不知道它在哪、什么时候该看。总管 CLAUDE.md 有一张「细则」表；子仓 CLAUDE.md 有「总管文档」和「细则」两张表。
- **路径一律写相对路径**，从这个文件所在的目录算起。绝对路径换一台机器、换一个人克隆就全部失效，而且在作者本机上看不出问题。
- **已有 `.claude/rules/` 的项目**：没写 `paths:` 的文件行数要算进开局；要不要挪进 `.agents/rules/`、或者加上 `paths:`，问用户，不自己挪。
- **总管 CLAUDE.md 会被子仓会话读到**（A 方案自动，B 方案带参数时）。所以包工头那句「不改代码」必须限定成「在总管目录启动时」，否则子仓会话会以为自己也不能写代码。
- **总管会话不要伸手改子仓**。除了分工，还有一个技术原因：实测里，总管会话读到子仓文件时，把子仓 CLAUDE.md 里和总管不一致的指令判成了可疑内容、拒绝执行。子仓的规矩只在子仓自己的会话里才可靠。
- **AGENTS.md 会被挤掉**。默认设置下，启动目录或它上面任何一层只要有 `CLAUDE.md`，所有 `AGENTS.md` 都不读，子目录里的也一样。所以根目录一有 CLAUDE.md，每个子仓的 AGENTS.md 就全部失效。处理办法：在同目录建 `CLAUDE.md`，写一行 `@AGENTS.md` 把它引进来（这是唯一推荐用 `@` 的地方，前提是 AGENTS.md 本身不超过 200 行），或者把内容并进 CLAUDE.md。团队里还有人用别的 AI 工具时，保留 AGENTS.md，用 `@` 引用；或者反过来，AGENTS.md 只留一句「规范全文在 CLAUDE.md，以那份为准」。

## spec：唯一真理源

- 按主题拆成带编号的文件，编号可以跳号，给以后扩展留位置。
- **章节号全局固定**：`§N.M` 指编号 N 的文件里的第 M 节，标题写成 `## §N.M 名称`，方便搜索。章节号永远不改、不复用；某节作废就保留标题，写「已废弃，改见 §x.y」。
- **别处只引章节号**：写「见 §6.2」，不复制原文。复制出去的内容迟早过时，AI 会拿着旧版本干活。
- **改契约的顺序**：先改 spec，再改代码。
- 已有 OpenAPI、Protobuf 这类机器可读的契约文件，问用户怎么处理，不自己挪。常见两种：手写维护的，可以挪进 `spec/`，不再手抄一份 Markdown；从代码生成的（比如由路由注释生成的 `openapi.json`），留在原仓，挪走会弄坏生成流程，在 INDEX.md 里登记它的位置和生成命令即可。

## plan：任务台账

- `plan/tasks.md` 是一张表，**所有任务都登记**，单仓的、跨仓的都算。一个任务一行。
- 只有台账里的状态算数。对话里说「做完了」不算，改了台账才算。
- 状态：`计划中` → `开发中` → `待验证` → `已完成`，另有 `待确认`（等别人拍板）和 `已废弃`。`待验证` 和 `已完成` 要分清：代码写完、能编译，但没在真实场景跑过，就是 `待验证`。
- 序号全局递增，不复用。废弃的任务不删行，状态改成 `已废弃`。台账的行不归档，留作历史。
- 谁登记：包工头派活时登记；子仓会话接到没登记过的活，自己先加一行再动手。
- 跨仓任务：台账一行，加一份 `joint-tasks/` 任务单，行里写上任务单文件名。台账只记状态和依赖，细节在任务单里。

## joint-tasks：联调任务单

- 两个以上的仓都要动的活才开单，一个任务一份文件，文件名是 `YYYY-MM-DD-短名.md`。
- 开工前先翻 `joint-tasks/`，有相关的就续写，没有再新建。
- 「契约变更」一节必须先在 spec 落地，各仓才能开始勾清单。
- 每个仓只勾自己那一栏。全部做完，对着联调验证清单逐项验收。
- 状态只有三个：`planning`、`in_progress`、`done`。一到 `done`，立刻移进 `_archive/joint-tasks/`，同时把台账那一行改成 `已完成`。这样 `joint-tasks/` 里只剩正在做的活，扫一眼文件名就知道在忙什么。

## 目录戒律

总管目录不许新增顶层文档。要新增，先对归属表：

| 想新增的 | 去哪 |
| --- | --- |
| 子仓内部说明 | 子仓自己的目录 |
| 跨仓的字段、接口 | `spec/` |
| 新任务、任务进度 | `plan/tasks.md` 加一行 |
| 正在做的跨仓任务 | `joint-tasks/` |
| 项目原有的跨仓文档类别（比如法律合规文本、品牌元信息） | 保持原位置，登记进总管 CLAUDE.md 的归属表 |
| 临时调研笔记 | 不建文件；实在要留，进 `_archive/` |

**例外**：确实跨仓、又归不进上面任何一类的文档，问过用户同意后，才能在总管目录新增顶层文件或目录。别把这条例外当成常规出口。

索引会过时。挪了或改名了文件，所有 CLAUDE.md 和 `.agents/rules` 里指向它的路径要同步改。

## 实际怎么用

同时开几个 Claude Code：

- **在总管目录开一个，当包工头**：只拆需求、派活、登记台账、改 spec、开任务单，不写业务代码。派活的方式是写一段能直接交给子仓会话的任务说明。
- **在每个子仓目录各开一个，负责干活**：读自己的 CLAUDE.md，按边界写代码，做完改台账状态。

子仓会话要读 spec、改台账、勾任务单、读总管的细则，这些都在它的启动目录之外，会弹权限确认。

- A 方案：`claude --add-dir ../spec ../plan ../joint-tasks ../.agents`
- B 方案：`CLAUDE_CODE_ADDITIONAL_DIRECTORIES_CLAUDE_MD=1 claude --add-dir ../<总管目录>`（这一条同时解决加载规则和读写权限）
